# Agent Plugin packaging and public review

Package the user's existing MCP server using the portable
[Agent Plugins specification](https://agent-plugins.org/specification) and its
[JSON schemas](https://agent-plugins.org/schemas). OpenAI directory requirements
are client-specific additions; check the target's current
[package guide](https://developers.openai.com/plugins/build/plugins) and
[submission guide](https://developers.openai.com/plugins/deploy/submission).
If Plugin Creator is available, its package and submission guidance can help
with the target workflow. Do not require that plugin to prepare local files.

## Portable layout

```text
my-plugin/
  plugin.json
  mcp.json
  skills/my-workflow/SKILL.md
  skills/my-workflow/references/
  assets/icon.png
```

Include only components the plugin uses. A remote MCP package declares its
connection; packaging does not deploy the server or require shipping its source
and dependencies. Skills-only packages can omit `mcp.json`.

Root `plugin.json` must declare the plugin schema and a stable lowercase name.
Use a semantic version for new packages and preserve identity on updates:

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "Describe the supported workflow.",
  "extensions": {
    "com.openai": {
      "interface": {
        "displayName": "My Plugin",
        "shortDescription": "A useful workflow",
        "longDescription": "Describe implemented behavior and intended users.",
        "capabilities": ["Read"],
        "logo": "./assets/icon.png",
        "composerIcon": "./assets/icon.png"
      }
    }
  }
}
```

This example is a package skeleton, not a completed public listing. Replace its
sample values with confirmed facts and add the required listing and review fields.
Portable clients discover `skills/` and `mcp.json` at fixed locations. Do not add
top-level `skills`, `mcpServers`, `apps`, or `interface` to the portable manifest.
Keep client settings in their extension namespace.

For a remote server, root `mcp.json` uses the matching schema and actual transport:

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/mcp.schema.json",
  "mcpServers": {
    "my-server": {
      "type": "streamable-http",
      "url": "https://mcp.example.com/mcp"
    }
  }
}
```

Replace the example URL with the verified deployed endpoint. Use the existing
transport and authentication. The portable core leaves authorization discovery
and credential storage to the client. OpenAI connection options, when needed,
belong under the server's `extensions.com.openai`; never put tokens, passwords,
or credential-bearing headers into the package. Do not invent an endpoint.

Each immediate `skills/<name>/SKILL.md` starts with YAML frontmatter containing
a matching `name` and a nonblank `description` explaining when to use it. Keep
workflow instructions in the skill and supporting detail in contained references.
Parse YAML and check relative links. Optional `agents/openai.yaml` uses its own
snake_case interface fields; it does not replace plugin listing metadata.

Retain an existing `.codex-plugin/plugin.json` compatibility overlay when the
target requires it, synchronizing identity, version, and presentation with the
portable source. A legacy `.mcp.json` does not replace root `mcp.json`.

## Public-upload copy

Preserve personal/workspace source and bindings. For an author-supplied OpenAI
directory ZIP, prepare a separate copy without root `.app.json` or any non-null
`apps` declaration, including `extensions.com.openai.apps` and declarations in
hidden compatibility manifests. Configure required integrations with verified
MCP endpoints in `mcp.json`. If an integration has only an app binding and no
supported MCP endpoint, report that packaging gap instead of dropping behavior.
Keep bindings generated by the portal in saved submissions and finalized releases.

Private exports follow their own installation rules and do not require public
review materials. Do not create a duplicate private plugin just to prepare a ZIP.

## Listing

Write public listing fields under `extensions.com.openai.interface`:

| Field | Guidance for OpenAI public submission |
| --- | --- |
| `displayName` | Clear name, at most 30 characters. |
| `shortDescription` | Purpose in at most 30 characters, including spaces and punctuation. |
| `longDescription` | Supported behavior and intended users, at most 4,000 characters. |
| `developerName` | The intended verified publisher; confirm the portal's saved identity. |
| `category` | A supported category in the target portal. |
| `defaultPrompt` | Up to three unique, single-line prompts, at most 128 characters each, without app mentions. Preserve supplied type and order on updates. |
| `websiteURL` | Public HTTPS page identifying the plugin and publisher. |
| `supportURL` | Public HTTPS page with a working support/contact route. |
| `privacyPolicyURL` | Published policy covering the actual data practices. |
| `termsOfServiceURL` | Published terms applying to the plugin. |
| `logo`, `composerIcon` | Contained relative paths to included square PNGs, at most 5 MiB each and at most 4096 × 4096 pixels. Logo: at least 256 × 256; composer icon: at least 48 × 48. |

All four listing URLs are required for public submission even though the portable
schema treats client metadata as optional. A root `homepage` or README links do
not populate them. Open the destinations, follow redirects, and inspect their
content and public accessibility. A successful HTTP status alone is insufficient.
Use confirmed data practices and publisher facts; draft text is not a published
policy. Leave unknown fields absent and track them as gaps.

Reuse supplied branding or help create a missing icon. Inspect the real file's
type, dimensions, size, and legibility. Optional dark-mode icons and brand colors
can be offered without blocking packaging; preserve existing choices on updates.

## Review and publication metadata

For each app needing initial review, prepare five distinct positive cases and
three negative cases from the implementation. Positive cases use natural prompts
and specify expected tools, important arguments, and observable results supported
by returned data. Negative cases should resemble the app's purpose while falling
outside its capabilities, specifying the explanation and prohibited tool use.
Authentication errors and empty results are supported-flow recovery cases, not
substitutes for negative capability cases.

Include reproducible setup and reviewer-accessible fixtures. Execute cases where
access and authorization allow, tracking Passed, Failed, Blocked, or Not run in
preparation notes. Do not add invented result fields to the manifest. Check that
tool annotations include accurate boolean `readOnlyHint`, `destructiveHint`, and
`openWorldHint` values.

Use exactly one review-case location:

- **One MCP server:** root `plugin.json`, at
  `extensions.com.openai.review.test_cases`, with `positive` and `negative`
  arrays. Each case has `description` and `prompt`. Positive cases also have
  `tools_triggered` and `expected_behavior` as strings. Optional evidence fields
  are `file_attachment_urls` and `expected_output_url`.
- **Multiple MCP servers:** each server in `mcp.json`, at
  `extensions.com.openai.review`, with `testCases` and `negativeTestCases`
  arrays. Cases use `description` and `userPrompt`; positive cases also have
  `toolsTriggered` and `expectedOutput`. Optional evidence fields are
  `fileAttachmentUrls` and `expectedOutputUrl`.

Other fields under `extensions.com.openai`:

| Field path | Value |
| --- | --- |
| `review.demo_recording_url` | Verified, reviewer-accessible video recording URL. |
| `publication.release_notes` | Supported changes in this release. |
| `publication.countries` | Confirmed supported country codes; omission preserves targeting, while an empty list deliberately removes restrictions. |
| `publication.translations` | Localized listing text keyed by locale; base listing fields provide English. |

Help record the packaged version using an existing development connection in the
intended host. Rehearse realistic prompts and actual results, then record and
inspect playback. Computer control or screenshots alone do not provide video
capture; use a recording tool or guide the user's recorder. Verify hosted playback
and reviewer permissions before writing the recording URL. A script, mockup, or
local video alone does not complete that field. Help resolve recording dependencies
while continuing independent package work.

Skills-only plugins need no MCP cases, recording, or reviewer credentials.
Existing reviewed dependencies require an eligible version rather than a new
initial review. Put dedicated reviewer-account credentials and login instructions
only in secure portal fields, never the ZIP or public listing. Verify the account
can access the sample data and features used in the cases.

## Archive and handoff

Build a ZIP or tar.gz containing one plugin directly at its root or inside one
enclosing folder without unrelated siblings. Write the archive outside the
directory being packaged. Exclude secrets, dependencies, symlinks, marketplaces,
and unrelated files. Include every referenced skill, icon, and supporting file.

Inspect the final archive, including hidden files. Parse JSON/YAML, validate the
portable manifests against the matching schemas and target-specific requirements,
check all contained paths, and review listing lengths, URLs, case counts, and
publication metadata. Rebuild and inspect after source edits. Use the project's
existing bundler when available; stage new inputs if it packages only tracked files.

Return the archive and specific remaining gaps. Package validity, runtime checks,
portal setup, and review approval are separate results. ZIP-only delivery retains
required metadata and preparation gaps without an upload. When requested, upload
as a draft, connect/authenticate the real server, test the saved version, and
verify imported metadata. Portal requirements can include developer/domain
verification, scans, secure reviewer access, and attestations by the authorized
developer. Submission for review and publication need their own authorization;
an upload alone completes neither.
